# Backend delivery

Implemented `backend/app.py` (FastAPI contract), `schemas.py` (side-effect-free API/model validation), `store.py` (durable SQLite transactional repository/queue/idempotency), `domain.py` (safety gates and complete lifecycle), `agent.py` (explicit simulator and bounded Bedrock child-process adapter), `coordinator.py` (one Strands agent with eight bound domain tools), `worker.py` (shared `process_run(repository, run_id)`), and backend tests. Dependencies and Python 3.12 environment are pinned in `uv.lock` from `pyproject.toml`.

Run `uv sync --python 3.12`, then `uv run uvicorn backend.app:app --host 127.0.0.1 --port 8000`. All endpoints use `/api`. Data defaults to `backend/data/neighborgear.sqlite3`; override `NEIGHBORGEAR_DB`. The default mode is `simulator`; no messages leave the application. Session tokens are hashed for authentication and never appear in snapshots. Session-creation idempotency responses include the original token and are kept internally to support retries; use a fresh cryptographically random Idempotency-Key for creation, as the key grants replay access to that creation response.

Every domain run is an atomic sandbox document transaction. Inventory checks and assignments execute inside that transaction. Failed commands roll back domain changes but persist their failed run and error event. Queue acknowledgements occur after state commits; a crash in between is repaired without replaying successful effects. Pending commands preserve per-session order through `has_predecessor(run_id)`. Approvals, reservations, assignments and loans are persisted collections in addition to request projections. Messages have domain deduplication keys. Mutating routes support Idempotency-Key, including session creation and reset.

Cloud repositories should implement `transaction(session_id)`, `get_run(run_id)`, `finish_queue(run_id,status)` and `has_predecessor(run_id)` with comparable atomicity and ordering. Queue records have id, session_id, payload (JSON object or string), status. `process_run` is the shared domain entrypoint. No live cloud deployment or Bedrock execution was performed.

Live mode uses `NEIGHBORGEAR_MODE=live`, requires `NEIGHBORGEAR_CREDITS_VERIFIED=true`, and uses AWS SDK credentials. Default model is `eu.amazon.nova-lite-v1:0`, default region `eu-west-1`, configurable with `BEDROCK_MODEL_ID` and `AWS_REGION`. The EU Nova Lite profile is documented in the [AWS model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-amazon-nova-lite.html). No Bedrock call has been made during development.

Every live command now runs through a single genuine Strands coordinator, including create, clarify, approve, lifecycle events and clock changes. Its eight tools are `read_request`, `search_inventory`, `propose_request`, `reserve_approved_equipment`, `assign_driver`, `record_lifecycle_event`, `advance_clock_and_remind`, and `write_outbox`. Tools perform actual trial-state outcomes; the worker persists their completed result atomically. The agent extracts text through the validated proposal tool, decides which bound workflow tools to invoke, inspects their results, and completes the simulated outbox. Tool execution is sequential, capped at 12 calls by SDK hooks, with a 60-second child-process deadline and no fallback. Failure or incomplete required steps returns no commit state. Large child-process results are drained before joining to avoid pipe-buffer deadlocks.

The model has no database handle, generic mutation tool, caller-supplied request selector, or authority to approve. Reservation accepts zero model arguments: its equipment ID and proposal version come exclusively from the already authenticated staff API command. Domain rules recheck availability, safety, deadlines and driver capacity before trial mutations. Messages use fixed domain templates/recipients and remain explicitly simulated. Creation/clarification stops at a persisted `human_handoff` event when staff approval or missing data is required. Staff approval resumes through a fresh persisted `/approve` command; this is durable application-level pause/resume, not an SDK interrupt requiring an open invocation.

Successful real coordination records `bedrock_used=true` plus model ID, tool count, performed domain tools and handoff state. A failed call with uncertain remote execution records null plus `bedrock_attempted=true`; gated calls record false. Fixture tests explicitly label themselves `strands_fixture` and false. Optional `NEIGHBORGEAR_JUDGE_KEY` requires a matching `X-Judge-Key` on session creation (checked before idempotent replay); absent configuration keeps local creation open. CORS permits that header and supports `NEIGHBORGEAR_CORS_ORIGINS` as a comma-separated allowlist.

Validation: `uv run pytest -q --tb=short` → **33 passed, 2 warnings in 0.94s**. The original 17 domain/API tests cover full lifecycle, reassignment, duplicate messages/loans, quarantine/inspection, unsafe/stale approvals, reservation/capacity races, auth/isolation, restart/replay/order, idempotency, rollback, retry, deadlines/windows, background consumption and deadline/credit gates. Sixteen coordinator tests use a scripted `strands.models.Model` with the actual Strands event loop/tool dispatcher, covering every command category, extracted facts/human handoff, self-approval rejection, incomplete/provider-failure rollback, actual 12-call exhaustion, judge/CORS guard, spawned large-state transport, worker commit/replay/rollback and Nova default/error handling. These are fixture orchestration tests, not inference evaluation. The two upstream Starlette/httpx deprecation warnings are non-failing. Bedrock extraction accuracy, live latency and AWS deployment remain unverified until user-owned access and credits are verified.

Local SQLite serializes writes across sandboxes; live coordination holds the transaction while running, prioritizing correctness over concurrent throughput. Move live work to a separately leased/persisted phase before public multi-user scaling. All seed identities, addresses, inventory and delivery events are fictional. The simulator recognizes explicit equipment names, North/Central/South, `80-95 cm`, `90 kg`, ISO dates and 24-hour `HH:MM` windows; it leaves unsupported or unstated information missing. Live extracted facts are schema-validated and require staff review, but semantic extraction accuracy cannot be proven without real inference evaluation. The 60-second execution bound can add up to five seconds of child cleanup time.
